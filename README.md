# dsh-cache-diagnostics

DeepSeek Harness 的**前缀归因**缓存诊断：不只告诉你命中率，而是告诉你**缓存前缀在哪一条消息上断开的**。

DeepSeek 的缓存是前缀匹配——从第一条消息开始，第一处不同之后全部作废。所以真正有用的问题不是“命中率多少”，而是“从第几条开始变了”。

## 它长什么样

左侧图标列多一个「缓存诊断」图标（带状态点：绿=最近一次命中正常，黄=低命中，灰=还没有数据）。点开后在中间主面板显示整页：

- **最近一条**卡片：命中率、判定、首差、三桶（未缓存 / 缓存读 / 缓存写）、输出、模型；
- **全部请求**表格，每次模型请求一行：

| 列 | 含义 |
|---|---|
| 时间 | 请求发生时刻 |
| 会话 | 会话标题 |
| 轮·步 | 第几轮第几步 |
| 命中 | 缓存命中率，DSH 口径：`缓存读 ÷（未缓存＋缓存读＋缓存写）`；默认百分比，可切千分比 |
| 未缓存 / 缓存读 / 缓存写 / 输出 | provider 报告的 token 桶 |
| 系统 | 系统提示相对上一条请求是否变化（同/变） |
| 首条 | 上下文第一条消息本身是否变了 |
| 工具 | 工具目录是否变化 |
| 首差 | 与同会话上一条请求相比第一处不同的消息位置 |
| Δ | 消息条数变化 |
| 判定 | 前缀延续 / 前缀自 #k 断开 / 工具集变化 / 服务端未命中 / 无用量 |

「首差」取值：`同`（完全一致）、`尾+N`（只在尾部追加，前缀没变）、`#k`（第 k 条起断开）、`#k−N`（同上且变短）、`—`（没有上一条可比）。

## 怎么实现的

刻意**不注册任何 conversation Definition**。DSH 的对话引擎会把每个 Definition 放进同一次事务里跑，一个抛错就会把整个 Chat 带崩（历史回放时尤其明显）。所以：

- **Host 半**：`sessionQuery.readSession()` 读会话日志，把事件折叠成请求行（命中率、系统/工具变化、首差、Δ、判定），通过 `/cache-diagnostics/v2` 提供 JSON。按会话最后 seq 缓存，日志没变就不重算。
- **Client 半**：一个 `sidebar.panellist` 图标 + 一个 `main` 面板页；页面轮询接口（空闲 4s、后台计算中 12s、页面隐藏 30s），只渲染最新 300 行。

两边都只读，不写会话、不碰引擎。

## 安装

```bash
npm install
npm run build
dsh plugin --profile <你的profile> add link:<本目录绝对路径>
```

注意：**host 半的代码只在 DSH 进程启动时加载**，改完 host 代码需要重启 DSH 才生效；只改 client 则刷新页面即可。

## 已知限制

- 只统计最近 **12 个会话**（按更新时间），避免一次读完整库；
- Host 首次全量折叠约 10–15 秒（两个上万请求的老会话占大头），期间接口返回 `pending` + 当前阶段；之后就靠 seq 缓存增量重算；
- 页面只渲染最新 300 行，总数在统计行里；完整数据在接口里；
- 「首差」基于会话日志里的 surface 身份（seq），不是内容哈希：DSH 保证未变更内容保留持久身份。
